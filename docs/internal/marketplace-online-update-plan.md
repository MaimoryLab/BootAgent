# 工具市场在线更新实施规范

## 目标

工具市场以嵌入式静态目录为稳定基线，并通过后端适配器增量发现 SkillHub 与 MCP
Servers 的公开数据。用户看到的卡片不能因为网络、缓存或某个数据源失败而消失；
搜索、筛选和滚动必须属于同一个查询会话，不能把不同查询的结果混在一起。

## 当前问题

- 首次进入只请求一次第一页，没有主动刷新入口或定时刷新。
- 磁盘缓存有效期过长时会短路网络请求，用户无法快速获取 SkillHub 更新。
- SkillHub 与 MCP 共用一个 offset，来源数量不同会导致跳页或截断。
- 请求没有查询版本，旧请求晚返回时可能覆盖新搜索结果。
- 滚动区域是 `.page-body`，监听 `window` 会使分页和虚拟列表失效。

## 设计决策

### 查询会话

前端为每次关键词、来源或分类变化生成递增的查询序号。请求携带完整查询条件；
响应只在序号仍然匹配时写入状态。查询序号不是安全凭据，只用于丢弃过期响应。

### 来源级分页

SkillHub 和 MCP Servers 各自维护 `offset`、`has_more` 和 `total`。后端一次请求只
访问指定来源的一页，返回 `next_offset`。前端不得根据返回条数猜测下一页，也不得
用一个来源的分页游标请求另一个来源。

### 搜索与筛选

- 关键词搜索传给远程适配器；SkillHub 使用 `keyword`。MCP Servers 目录使用公开的
  `/search?query=&page=` 页面，SkillHub 的 MCP API 仅作为有界补充和故障回退；必要时
  继续读取有限页以找到未加载的结果。
- 分类、场景、工具类型等产品维度在统一卡片集合上执行；不支持远程映射的维度不
  得伪装成远程精确筛选。
- 滚动请求复用当前查询条件和查询序号。

### 刷新与缓存

- 首次进入立即请求第一页；有效磁盘缓存只能作为失败回退，不能阻止首屏网络请求。
- 提供用户可触发的强制刷新，并在页面停留期间按 10 分钟间隔后台刷新第一页。
- 无查询条件的第一页使用 ETag；304 时复用缓存并更新抓取时间。
- 刷新期间保留现有卡片，不能显示空白页。

### 合并规则

- 静态目录优先，动态卡片追加在静态卡片之后。
- 以稳定 ID 去重，再以来源 URL/仓库 URL 做跨版本兜底；只有缺少稳定 URL 的旧记录才
  使用 `source + normalized name`，避免同名 MCP Server 被错误合并。
- 动态源失败时保留静态卡片，并在数据源状态中显示 `cached` 或 `unavailable`。

## API 契约

`MarketplaceService.DiscoverSources` 接收：

```json
{
  "source": "skillhub",
  "query": "",
  "category": "",
  "limit": 50,
  "offset": 0,
  "force_refresh": false,
  "query_id": "q-12"
}
```

响应至少包含：

```json
{
  "items": [],
  "sources": [],
  "total": 0,
  "has_more": false,
  "next_offset": 0,
  "query_id": "q-12",
  "stale": false,
  "fetched_at": ""
}
```

`sources` 中每个来源必须报告 `id`、`state`、本次或缓存的 `item_count`、
`total`、`fetched_at` 和可展示的错误摘要。错误摘要不得包含响应正文、密钥或本地
敏感路径。

- [x] 切换分类/来源后，结果只属于当前条件，静态基线不消失。
- [x] 真实 Wails 浏览器测试覆盖加载、刷新、搜索、滚动和错误回退。

## 实施记录

- 后端为 SkillHub 与 MCP Servers 建立独立来源适配器、分页游标、查询 ID、强制刷新、
  ETag 和受限缓存回退；静态目录始终作为首屏基线。MCP 列表主源使用
  `https://mcpservers.org/all` 与 `/search` 的公开分页 HTML，SkillHub 的
  `https://api.skillhub.cn/api/v1/mcp/servers` 保留为有界补充和故障回退；详情与 README
  从 mcpservers.org 的服务端序列化记录按需解析。旧 SkillHub slug 详情仍使用单条接口，
  README 使用 `/readme` 接口并由 Go 跟随 COS 重定向。
- 前端以查询会话隔离请求，按来源并发分页，滚动触发后续页；短结果集会有限度自动
  补页，避免本地场景/类型筛选后没有滚动事件而永远看不到后续匹配项。
- 卡片以静态目录优先、动态结果追加，并按 ID 与稳定来源 URL 去重；详情页携带动态卡片
  快照，后续页的工具不会因重新创建查询而丢失详情。
- 数据源状态显示实时/缓存/不可用及已加载数/总数；刷新期间保留已有卡片。
- MCP 详情页按需合并实时名称、来源、仓库、官网、统计和安装提示词；README 通过
  Wails binding 延迟加载并在 renderer 中进行 Markdown 清理，避免 CORS 和不可信 HTML。
- 设置页的版本 binding 增加字符串边界校验，避免浏览器预览或旧 binding 返回结构化
  错误对象时导致 React 渲染崩溃。

## 风险与边界

- SkillHub 总量很大，禁止为了刷新首屏遍历全量页面；后台刷新只拉第一页，后续由
  用户滚动驱动。
- 外部 API 是公开但非稳定协议，所有字段必须容错解析，适配器失败不得阻塞静态市场。
- 本地埋点只保存聚合事件，不记录搜索正文、URL 查询中的密钥或 README 内容。

## 发布前修复阶段

以下问题来自对最新远程 `main` 的只读审查，完成前不得将该阶段标记为通过。

### 任务 1：统一导入事务与失败回滚（P1）

**目标：** v2 导入在任意资源校验或写入失败后，Provider、Profile、MCP、Skill
注册表和 Skill 文件均恢复到导入前状态。

**验收标准：**

- [x] 导入前快照所有受影响资源，快照对象在执行过程中不可变。
- [x] 所有内容完成校验后再提交写入；失败时不留下部分配置或幽灵 Skill 路径。
- [x] 回滚使用独立 context，且回滚失败会被记录并返回可诊断错误。
- [x] 覆盖跨资源失败、Skill/MCP 失败和快照恢复测试。

**依赖：** 无。  **风险：** 高。  **涉及：** `internal/app/transfer.go`、
`internal/transfer/*` 及对应测试。

### 任务 2：运行时替换增加可恢复发布（P1）

**目标：** 新运行时发布失败时保留旧版本，避免 `RemoveAll` 后重命名失败造成运行时
丢失。

**验收标准：**

- [x] 旧目录先进入同级回滚目录，新目录发布成功后才删除回滚目录。
- [x] 模拟重命名失败时，旧运行时仍可启动。
- [x] 发布成功、失败恢复和残留清理均有替换逻辑测试。

**依赖：** 无。  **风险：** 高。  **涉及：** `internal/install/bootstrap.go`。

### 任务 3：限制 ZIP 总资源消耗（P1/P2）

**目标：** 防止外层 ZIP 或嵌套 `skills.zip` 通过高压缩比和大量条目耗尽内存或磁盘。

**验收标准：**

- [x] 限制外层、嵌套 ZIP 和单 Skill 的累计解压字节数、条目数和 Skill 数量。
- [x] 解析过程不使用无上限 `io.ReadAll`，超限时在写入前失败。
- [x] 覆盖高压缩比、重复条目、嵌套 ZIP 超限和边界大小测试。

**依赖：** 任务 1 的导入提交边界。  **风险：** 高。  **涉及：**
`internal/transfer/v2.go`、Skill 解包逻辑及测试。

### 任务 4：更新源一致性与官方回退（P2）

**目标：** Gitee 等镜像滞后或返回“无更新”时，客户端仍能发现 GitHub 的新版本。

**验收标准：**

- [x] 镜像无更新且本地版本低于官方版本时继续比较官方元数据。
- [x] 下载源和展示源可分离，镜像可用时仍优先使用镜像下载。
- [x] 覆盖镜像滞后、镜像错误、官方错误和两源版本一致的测试。

**依赖：** 无。  **风险：** 中。  **涉及：** `cmd/bootagent-desktop/main_wails.go`、
更新器测试。

### 任务 5：导入冲突预览与确定性合并（P2）

**目标：** 用户在确认前看见新增、覆盖和冲突项，重复 Skill 不得静默覆盖。

**验收标准：**

- [x] 预览列出 Provider/Profile/MCP/Skill 的冲突名称。
- [x] 重复归一化 ID 被明确阻止或要求选择处理策略，结果与 ZIP 条目顺序无关。
- [x] 前端确认请求携带明确的覆盖/跳过策略，后端再次校验该策略。

### 任务 6：市场查询请求治理（P2）

**目标：** 快速输入或连续筛选不会产生请求风暴，旧响应不会污染当前结果。

**验收标准：**

- [x] 搜索输入使用 debounce，新的查询通过查询序号隔离旧响应。
- [x] 单次查询有总页数、总响应大小和上游请求预算。
- [x] 快速输入、断网恢复和重复查询测试验证最终结果只属于最后一次查询。

**依赖：** 现有查询会话与来源级分页。  **风险：** 中。  **涉及：**
`frontend/src/components/ManagementSearch.tsx`、`frontend/src/data/useMarketplaceCatalog.ts`、
`internal/app/marketplace_dynamic.go`。

### 任务 7：详情返回恢复搜索与筛选状态（P1 交互）

**目标：** 用户从市场列表搜索或筛选后进入详情，再返回时，回到原查询上下文，不被
重置到初始市场页面。

**设计：** 将关键词、来源、分类、工具类型、场景/领域筛选、排序、分页游标和列表
滚动位置视为同一个查询会话状态。进入详情时通过路由 state（必要时退回 sessionStorage）
保存快照；返回优先恢复最近一次有效的搜索/筛选快照，确保用户不会丢失刚才的查询上下文。
即使详情页通过直接链接打开，只要本地仍保留最近一次市场查询，也继续回退到该查询；没有历史
查询时才使用默认市场页。

**验收标准：**

- [x] 搜索后进入详情再返回，搜索框内容、筛选项、结果数量和滚动位置保持不变。
- [x] 多选工具类型返回后不重复、不丢失静态卡片，来源分页游标与当前查询一致。
- [x] 浏览器后退、详情内返回按钮、刷新详情页和新标签打开详情均有明确行为。
- [x] 增加 Vitest 状态恢复测试和 Playwright 真实导航回归测试。

**依赖：** 现有查询会话、来源级分页和虚拟列表。  **风险：** 中。  **涉及：**
`frontend/src/pages/MarketplacePage.tsx`、`frontend/src/data/useMarketplaceCatalog.ts`、
路由状态工具及 E2E 用例。
